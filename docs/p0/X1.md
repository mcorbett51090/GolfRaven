## Recorded export

_(blank until Matt logs each OS's UTC date, BEFORE that OS's export is read — decision 0005 "Integrity
rules": "The first export read is the recorded one ... The same rule applies separately to each OS."
Format `YYYY-MM-DD` (UTC). `x1-ios-export`/`x1-verdict` refuse to produce a RECORDED result for an OS
whose line here has no UTC date logged; `--informational` runs anyway — **but only against a synthetic
fixture under `tools/p0/test/fixtures/`, never real device data, while that OS is unbound (round-3
Opus-gate correction, post-8e5a29b: "no informational runs on real data while an OS is unbound"),
whether the date is still blank or already logged.** Once an OS is bound (its SHA-256 recorded, below),
`--informational` may run against any path, including real data — it just never overwrites or feeds
the recorded result. A later export can still be read informationally — it never replaces the recorded
result once one exists for that OS.)_

**Bound to one specific export — and recomputed fresh every recorded run, never stored.** The tools
check that the export's own UTC date (Apple's `ExportDate` for iOS; the Android reader's own
`generatedAt` for Android — both re-read fresh from the real file, never trusted from a JSON field)
matches the UTC date logged here, and — on the first recorded run — append that export's SHA-256 to the
SAME line as `sha256:<hex>` (e.g. `- iOS: 2026-09-20 sha256:abcd...`), printing **"commit and push
docs/p0/X1.md now."** Every later recorded run for that OS must supply that OS's bound file again and
hash it to the same value, or it's refused: a recorded result is bound to one specific export file, not
just one calendar date, and re-verified from that file every single time — **this line never stores a
`result:` of its own.** A recorded `x1-verdict` run needs the bound input of every OS this file already
shows as bound (a missing one is refused, not silently skipped), recomputes each supplied OS's
pass/kill straight from its bound file, and combines them in that one call: the overall result is a
pass when **any** bound OS recomputes to pass. Nothing about the result is ever read back from this
markdown file — only the UTC date and the SHA-256 are.

**The first-bind trust limit.** Whichever file is bound first for an OS — iOS's `export.xml`, or
Android's raw reader-output JSON — is trusted as that device's genuine output; nothing here can verify
it further, on either OS.

**A binding run prints no verdict (round-4 Opus-gate correction, post-4279773).** The run that performs
an OS's FIRST bind — writes its `sha256:` for the first time — stops there: it prints **"bound: commit
and push docs/p0/X1.md, then re-run"** and never computes or prints a verdict, a per-source detail, or
writes a result file from a binding that hasn't even been pushed yet. Only a LATER run, made against a
hash that already matches what's committed, recomputes and reports the actual result. This closes a gap
in the trust limit above: a bind and its verdict used to happen in the same call, so a verdict could be
seen (and acted on) before the bind was ever pushed anywhere.

**Refuse a second binding (round-4 Opus-gate correction, post-4279773).** Deleting (or reverting) a
bound `sha256:` suffix and committing that made an OS's line read as unbound again — so the very next
run would silently bind it to a DIFFERENT export, with no one having decided a re-bind was warranted.
Before writing a hash, the tools now scan `docs/p0/X1.md`'s own git history for a previous bind of that
OS's line (even one since deleted/reverted); if history shows one, the run refuses with **"re-binding
needs an owner decision"** — deciding to trust a different export than the one first bound is not this
tooling's call to make silently.

**Verdicts come only from a committed binding (round-4 Opus-gate correction, post-4279773).** A recorded
run — a bind OR a verdict — refuses outright while `docs/p0/X1.md` has any uncommitted change. A
recorded result must always reflect what's actually committed, never a working copy that could be
edited and discarded right after. **If git itself is unavailable, or `docs/p0/X1.md` isn't inside a real
git repository, a recorded run refuses** — these checks are load-bearing, not best-effort.

**What this does and doesn't protect against.** The SHA-256 binding catches a *later* run being given a
*different* file than the one first bound; the git-history scan above catches a *delete-then-rebind*.
Neither detects local git history being rewritten in place (a `rebase`/`commit --amend` could edit a
past commit's bound hash without leaving a trace visible from the working tree) — earlier machinery
that tried to catch that directly (a broader tampering scan, a shallow-clone refusal) was removed as
unneeded once the design stopped storing a result to protect. The actual protection remains procedural,
the same one decision 0001 Addendum F relies on for K2's exclusion dating: **commit AND PUSH
`docs/p0/X1.md` to GitHub immediately after a binding run** — a pushed commit is anchored outside any
one local clone's history, so a later local rewrite can't quietly change what was bound. This is why a
binding run prints "commit and push `docs/p0/X1.md`, then re-run," not just "commit."

## METHOD

1. Play one real round of golf carrying: a Garmin golf watch running Garmin Connect Mobile; an Apple Watch
   running a Workout (Golf activity type where offered); and **18Birdies** as the phone golf app (Hole19 as
   the pre-round fallback if 18Birdies cannot be installed or offers no Health write setting — decision 0001,
   Addendum D, R6; both are on the plan's no-public-API app list, §7.3 row "—").
2. After the round, on the iPhone: **Settings → Health → profile icon → Export All Health Data**, producing
   `export.zip` (containing `export.xml` and a `workout-routes/` folder of GPX files per workout)
   `[unverified — training knowledge]`.
3. Inspect `export.xml` for each of the 3 sources' `<Workout>` elements: record `workoutActivityType`,
   `HKSource.bundleIdentifier`, and whether a matching GPX route file exists in `workout-routes/` (⇒
   `HKWorkoutRoute` present).
4. Run the equivalent round (or a second round) on Android with Health Connect enabled, using the P0-skeleton
   Health Connect reader (`apps/mobile` — built and unit-tested as of 2026-09-23, but **not device-tested**;
   see `apps/mobile/README.md` "Not device-tested" — a 0.5 pw prerequisite, reused by P4)
   to read the exercise type, route, and `dataOrigin` for each source that also has an Android app.
5. Record a **verdict per source** (Garmin, Apple Watch, phone app) × per OS, not just an overall pass/fail
   (A2-14) — a Garmin-source fail must stay visible even if the other two sources pass.
6. **CONSENT_REQUIRED rule (decision 0001, Addendum D, R6):** on Android, a session that Health Connect
   reports as `CONSENT_REQUIRED` counts as "route present" **only if** a follow-up `requestExerciseRoute` for
   that session's record id returns at least one point. Otherwise it counts as "not present". This is decided
   now, before the round, not after seeing which way a real result falls.
7. **The phone golf app is 18Birdies** (decision 0001, Addendum D, R6), fixed before the round. If 18Birdies
   cannot be installed, or offers no Apple Health / Health Connect write setting, **Hole19 replaces it**, and
   the reason is logged in this memo's Log below before the round. Any other app tried is supplementary data,
   never the source verdict.
8. **Every golf workout on the device counts, not just ones inside a logged round window (decision 0005).**
   A logged "Round windows" entry only tags a matching workout `testRound: true` in the tools' output; it does
   not gate whether the workout counts. Historical rounds on Matt's Garmin Approach S62 count the same as a
   newly-played one — their route must still be present, exactly as before.
9. **Log the "Recorded export" UTC date for an OS BEFORE reading that OS's export (decision 0005).**
   `x1-ios-export` takes `--os ios`; `x1-verdict` takes `--ios-export <apple_health_export-dir>` and/or
   `--android <health-connect-reader.json>` (at least one required — no `--os` flag on `x1-verdict` any more,
   since it recomputes whichever OS(es) it's given). Both refuse to produce the RECORDED result for an OS
   whose UTC date is still blank. `--informational` runs anyway, but **only against a synthetic fixture under
   `tools/p0/test/fixtures/`, never real device data, while that OS is unbound** (round-3 Opus-gate correction,
   post-8e5a29b, superseding round 2's narrower "no peeking only in the logged-but-unbound gap" — now it's
   "no informational runs on real data while unbound," full stop, whether the date is blank or already
   logged). Once an OS is bound, `--informational` may run against any path. The first export actually read
   for an OS, with its UTC date logged first, is that OS's recorded one; a later export is informational only.
   `x1-ios-export`/`x1-verdict` bind the run to that specific export — its own UTC date and a fresh SHA-256 of
   the real file, never a value read out of a JSON field, compared against what's logged/bound.
10. **A recorded X1 verdict is decided per OS, RECOMPUTED FRESH from that OS's bound file every single time —
    nothing is ever stored or read back (round-3 Opus-gate correction, post-8e5a29b, simplifying round 2's
    `result:`-line/git-log-scan design — "fix by simplifying, not by adding more integrity machinery").**
    `x1-verdict` never trusts any `recorded`/`os` field inside a JSON's own claims; instead, for each OS it's
    given a bound input for, it verifies that input's UTC date and SHA-256 against `docs/p0/X1.md` and then
    recomputes that OS's pass/kill straight from the verified data, in the same call. If `docs/p0/X1.md` shows
    an OS as already bound but its input wasn't supplied this run, the run is refused outright — a recorded
    verdict is never computed from a partial picture. The overall recorded result is "pass if any supplied,
    bound OS recomputes to pass" (Addendum F's ≥ 2-of-3-on-one-OS bar, applied within that OS's data only),
    decided in-process from however many OSes this one call recomputed — never by reading a stored verdict
    back out of the markdown file. The Android reader (`apps/mobile/src/health-connect/`) emits `os: "android"`
    and `generatedAt` as part of its own real output now, not as a hand-added annotation — `x1-verdict` refuses
    an `--android` file missing either field as a basic shape check, not a trust mechanism (whatever file binds
    an OS first is trusted as that device's genuine output either way — see "Recorded export" above).
11. **A binding run stops before producing any verdict; a verdict only ever comes from a committed binding
    (round-4 Opus-gate correction, post-4279773).** The run that performs an OS's FIRST bind prints "bound:
    commit and push docs/p0/X1.md, then re-run" and exits without computing or printing anything else — commit
    and push, then run again, and THAT run recomputes and reports the actual result. Deleting/reverting a bound
    `sha256:` line and re-running does **not** quietly reopen it: the tools scan `docs/p0/X1.md`'s own git
    history first and refuse with "re-binding needs an owner decision" if that OS was ever bound before. Every
    recorded run (bind or verdict) also refuses outright while `docs/p0/X1.md` has any uncommitted change, or
    if git itself isn't available. See "Recorded export" above for the full mechanics.
