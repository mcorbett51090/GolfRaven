## Recorded export

_(blank until Matt logs each OS's UTC date, BEFORE that OS's export is read — decision 0005 "Integrity
rules": "The first export read is the recorded one ... The same rule applies separately to each OS."
Format `YYYY-MM-DD` (UTC). `x1-ios-export`/`x1-verdict` refuse to produce a RECORDED result for an OS
whose line here has no UTC date logged; `--informational` runs anyway, producing an output marked
`recorded: false` with a loud banner, never the recorded P0 result — **except** in the window between
the UTC date being logged and its hash being bound (round-2 Opus-gate correction, post-67bdb27), where
even `--informational` is refused ("no informational peeking before binding"; use a synthetic test
fixture for a dry run in that window). A later export can still be read informationally — it never
replaces the recorded result once one exists for that OS.)_

**Bound to one specific export.** The tools also check that the export's own UTC date (Apple's
`ExportDate` for iOS; the Android reader's `generatedAt` for Android — both re-read fresh from the real
file, never trusted from a JSON field) matches the UTC date logged here, and — on the first recorded
run — append that export's SHA-256 to the SAME line as `sha256:<hex>` (e.g.
`- iOS: 2026-09-20 sha256:abcd...`), printing **"commit docs/p0/X1.md now."** Every later recorded run
for that OS must hash to the same value, or it's refused: a recorded result is bound to one specific
export file, not just one calendar date. `--informational` is never checked against, or bound to, any
of this.

**Each OS's own recorded X1 result is ALSO written here (round-2 Opus-gate correction, post-67bdb27),
as `result:pass` or `result:kill` on the same line** (e.g.
`- iOS: 2026-09-20 sha256:abcd... result:kill`) — computed from that OS's own data alone, never
silently overwritten by a later run that disagrees. This is what lets the two OS passes combine
without ever sharing data in one call: X1's overall result is a pass when **either** OS's own
`result:` here is `pass`.

**Git-history + working-tree integrity (should-fix, post-67bdb27).** Before binding, a recorded run
also refuses in a shallow git clone, when this file has uncommitted changes, or when its full git
history shows a bound hash was ever changed or removed after being set — in the spirit of decision
0001 Addendum F's `git log -S` precedent for K2's exclusion dating (this uses `-G`, since a hash VALUE
swap, not just an add/remove of the literal "sha256:" substring, is what needs catching).

## METHOD

1. Play one real round of golf carrying: a Garmin golf watch running Garmin Connect Mobile; an Apple Watch
   running a Workout (Golf activity type where offered); and **18Birdies** as the phone golf app (Hole19 as
   the pre-round fallback if 18Birdies cannot be installed or offers no Health write setting — decision 0001,
   Addendum D, R6; both are on the plan's no-public-API app list, §7.3 row "—").
2. After the round, on the iPhone: **Settings → Health → profile icon → Export All Health Data**, producing
   `export.zip` (containing `export.xml` and a `workout-routes/` folder of GPX files per workout)
   `[unverified — training knowledge]`.
3. Inspect `export.xml` for each of the 3 sources' `<Workout>` elements: record `workoutActivityType`,
   `HKSource.bundleIdentifier`, and whether a matching GPX route file exists in `workout-routes/` (⇒
   `HKWorkoutRoute` present).
4. Run the equivalent round (or a second round) on Android with Health Connect enabled, using the P0-skeleton
   Health Connect reader (`apps/mobile` — built and unit-tested as of 2026-09-23, but **not device-tested**;
   see `apps/mobile/README.md` "Not device-tested" — a 0.5 pw prerequisite, reused by P4)
   to read the exercise type, route, and `dataOrigin` for each source that also has an Android app.
5. Record a **verdict per source** (Garmin, Apple Watch, phone app) × per OS, not just an overall pass/fail
   (A2-14) — a Garmin-source fail must stay visible even if the other two sources pass.
6. **CONSENT_REQUIRED rule (decision 0001, Addendum D, R6):** on Android, a session that Health Connect
   reports as `CONSENT_REQUIRED` counts as "route present" **only if** a follow-up `requestExerciseRoute` for
   that session's record id returns at least one point. Otherwise it counts as "not present". This is decided
   now, before the round, not after seeing which way a real result falls.
7. **The phone golf app is 18Birdies** (decision 0001, Addendum D, R6), fixed before the round. If 18Birdies
   cannot be installed, or offers no Apple Health / Health Connect write setting, **Hole19 replaces it**, and
   the reason is logged in this memo's Log below before the round. Any other app tried is supplementary data,
   never the source verdict.
8. **Every golf workout on the device counts, not just ones inside a logged round window (decision 0005).**
   A logged "Round windows" entry only tags a matching workout `testRound: true` in the tools' output; it does
   not gate whether the workout counts. Historical rounds on Matt's Garmin Approach S62 count the same as a
   newly-played one — their route must still be present, exactly as before.
9. **Log the "Recorded export" UTC date for an OS BEFORE reading that OS's export (decision 0005).**
   `x1-ios-export` and `x1-verdict` both take `--os ios|android` and refuse to produce the RECORDED result for
   an OS whose UTC date is still blank; pass `--informational` to run anyway (the output is then marked
   `recorded: false` with a loud banner) **except in the gap between logging the date and binding the hash**,
   where `--informational` is refused too (round-2 Opus-gate correction, post-67bdb27: "no informational
   peeking before binding" — use a synthetic fixture for a dry run there instead). The first export actually
   read for an OS, with its UTC date logged first, is that OS's recorded one; a later export is informational
   only. `x1-ios-export`/`x1-verdict` also bind the run to that specific export — its own UTC date and a fresh
   SHA-256 of the real file, never a value read out of a JSON field, compared against what's logged/bound —
   and refuse in a shallow clone, on an uncommitted `docs/p0/X1.md`, or if git history shows the bound hash
   was ever changed (see the "Recorded export" section above).
10. **A recorded X1 verdict is decided per OS, from that OS's own INDEPENDENTLY VERIFIED data alone
    (round-2 Opus-gate correction, post-67bdb27, superseding the earlier "hand-stamp `recorded: true`"
    design).** `x1-verdict --os ios` never trusts any `recorded`/`os` field inside a JSON — it re-derives
    iOS's verdict from a completely fresh re-parse of `export.xml` itself (refusing if that disagrees with
    the `--ios` JSON's own claimed workouts — a tamper signal) and, for Android, relies on the fact that the
    whole `--android` file is what's hashed and bound, so any tampering of its data is caught by the hash
    check on a re-run. The OTHER OS's data, if passed alongside, is shown for cross-reference but never folds
    into the recorded result. Each OS's own recorded result is written into `docs/p0/X1.md` as
    `result:pass`/`result:kill`, so the two runs — however far apart, in however many separate invocations —
    combine by reading that file back, never by sharing input data. X1's overall recorded result is "pass if
    either OS's own recorded `result:` is pass" (Addendum F's ≥ 2-of-3-on-one-OS bar, applied within that OS's
    data only); "pending" until both OSes have recorded one.
