## METHOD

Query the public Overpass API (`https://overpass-api.de/api/interpreter`).

### 1. US+CA `leisure=golf_course` count (`N_osm`) — the pace measurement, not pass/fail

```overpassql
[out:json][timeout:180];
area["ISO3166-1"="US"][admin_level=2]->.us;
area["ISO3166-1"="CA"][admin_level=2]->.ca;
(
  way["leisure"="golf_course"](area.us);
  relation["leisure"="golf_course"](area.us);
  way["leisure"="golf_course"](area.ca);
  relation["leisure"="golf_course"](area.ca);
);
out count;
```

Record the returned `total` as `N_osm`. `swc-analysis.md §10.2` cites "~15k facilities" for a comparable
directory scale `[training knowledge]` — this query gets the real OSM number, not an estimate.

### 2. Polygon coverage on the pilot-candidate courses — the pass/fail measurement

(`golf=hole` coverage is measured alongside for coverage quality, but the pass bar itself is about
**`leisure=golf_course` polygon presence**, not `golf=hole` — see "Coverage calculation" below.)

**Pre-registered before this query is run** (gate review S12):

- **Unit:** matches X2's `completionUnit` for each trail (course, facility, or hole — SP7; X2 settles which
  per trail). Where `completionUnit = 'course'`, coverage is counted per course even if several courses
  share one facility polygon (RTJ: 26 courses at 11 sites) — a shared facility polygon counts for **every**
  course at that facility, since one polygon genuinely covers all of them, but it is still one data point
  per course in the denominator, not one per facility.
- **Match rule:** a candidate `leisure=golf_course` way/relation counts for a given pilot-candidate course
  only if **it contains that course's known point** (from X2's roster, once fetched), or, when no point is
  available, is **name-matched within a 500 m radius** of the course's approximate location. **Not** "any
  `leisure=golf_course` polygon returned by the bbox query" — a bbox can return a neighbour's polygon and
  would inflate coverage if counted uncritically.

This needs a bounding box (or centroid + radius) **per pilot-candidate course**, which is not yet known —
X2's direct fetch of the TN / VI / RTJ rosters supplies the course list and locations first. Once that list
exists, run one query per course (or a single query unioning all bboxes) of this shape:

```overpassql
[out:json][timeout:60];
(
  way["leisure"="golf_course"](<south>,<west>,<north>,<east>);
  relation["leisure"="golf_course"](<south>,<west>,<north>,<east>);
);
out geom;
(
  way["golf"="hole"](<south>,<west>,<north>,<east>);
  relation["golf"="hole"](<south>,<west>,<north>,<east>);
);
out count;
```

Run once per course in the pilot-candidate list (TN's 9, VI's 11–13, RTJ's 26 at 11 sites — **to be filled
from X2's confirmed roster**), using each course's approximate location (from the trail's own site, or a
first Overpass name search if the trail site doesn't give coordinates). A bbox query can return more than
one `leisure=golf_course` result (e.g. a neighbouring course or facility) — apply the pre-registered match
rule above (contains the course's point, or name-matched within 500 m) to decide whether **this** course
has a matching polygon; do not count "any polygon returned by the bbox." Record, per course: whether a
matching `leisure=golf_course` way/relation exists (the "has an OSM polygon" pass criterion), and
separately whether `golf=hole` ways exist within it (a coverage-quality measurement, not itself pass/fail
per this check's bar).

### 3. Other §5.2 pace measurements (recorded alongside, not pass/fail)

### Coverage calculation

`% with polygon` = (pilot-candidate courses with a `leisure=golf_course` way/relation found) / (total
pilot-candidate courses). Compute both combined and per-trail, since the kill consequence's manual-polygon
fallback is scoped "before P1" for whichever courses lack one, not necessarily the whole slate.
