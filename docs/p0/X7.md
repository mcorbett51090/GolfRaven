## METHOD

Full runnable kit: `docs/owner/x7-postgis-benchmark.sql` (schema + synthetic ~2k-polygon data + the timed
point-in-polygon query) and `docs/owner/x7-postgis-benchmark.md` (how to run it and read p95).

Summary:

1. Confirm `postgis` is available as an extension on the chosen Supabase project/tier: `create extension if
not exists postgis;` must succeed.
2. Build a synthetic ~2,000-row polygon table (buffered points scattered across the US+CA bounding box) with a
   GiST spatial index, standing in for the eventual `catalog_facility`/`catalog_course` polygon set (§4.4) at
   pilot-adjacent scale (X5's `N_osm` gives the real eventual count once measured).
3. Run 1,000 point-in-polygon queries (`ST_Contains`) and record the **p95** latency, measured **in-database**
   via a `clock_timestamp()` PL/pgSQL timing loop (equivalently, per-query `EXPLAIN ANALYZE` execution time)
   — not client round trip, not end-to-end from the Edge Function region (decision 0001, Addendum B). The
   1,000 query points are generated so that **roughly half fall inside a polygon and half do not** (half via
   `st_pointonsurface` on a randomly chosen polygon, half uniform-random over the bbox), with each point
   bound once via `\gset` before timing starts — never `random()` evaluated inside the predicate. The **hit
   rate is reported alongside p95**; a hit rate near 0% or near 100% means the point generation didn't work
   as intended and the run is not recorded as the result. **The first complete run on the chosen Supabase
   tier is the recorded result.**
4. Pass bar: PostGIS extension present **and** measured p95 < 100 ms.

Region note: §3.7 lists the prod Supabase project (`gr-prod`) as "NA region `[unverified — training
knowledge]`" — the plan does not commit to a specific sub-region (e.g. `us-east-1` vs `ca-central-1`); that
choice is made when the project is created (see `docs/owner/accounts-and-domain-checklist.md`).
